# EDMO Document Intelligence Engine (LLM Backend) v0.1

The **EDMO DI LLM Backend** is the semantic interpretation and structured extraction service for the EDMO Document Intelligence platform. It consumes loss-aware `llm_context.json` produced by the EDMO C++ OCR Engine and orchestrates structured semantic extraction using a locally hosted LLM (Ollama + Qwen3-8B).

---

## 1. Core Architectural Principles

- **The LLM is NOT the source of truth**: The document evidence generated by OCR + Full EDR + Loss-Aware Context Builder is the source of truth.
- **Candidate Data Pipeline**: LLM output is strictly treated as *candidate data* until verified through schema validation, evidence cross-referencing, hallucination detection, and deterministic normalization.
- **Evidence vs Schema Separation**: A candidate field may pass schema validation (e.g. `{ "course_code": "CS999" }`) but will be flagged as `UNSUPPORTED_BY_EVIDENCE` if it does not exist in the supplied document evidence.
- **Adversarial & Injection Resilience**: Document content is isolated in `DOCUMENT_EVIDENCE` blocks and treated as untrusted data.
- **Auditable & Non-Destructive**: Every step of the extraction pipeline generates preserved JSON artifacts.

## 2. Architecture & Data Flow

```
                     INPUT DOCUMENT
                           │
                           ▼
                  ┌─────────────────┐
                  │ EDMO OCR ENGINE │ (C++)
                  └────────┬────────┘
                           │
                           ▼
                  LOSS-AWARE CONTEXT
                   llm_context.json
                           │
                           ▼
           ┌────────────────────────────────┐
           │     EDMO DI LLM BACKEND        │
           │                                │
           │ 1. Context Validator           │  (Loss Gate: unaccounted_loss == 0)
           │ 2. Prompt Builder              │  (transcript.v1 + Injection Defense)
           │ 3. LLM Gateway                 │  (Ollama Provider Abstraction)
           │ 4. Response Parser             │  (Extracts Candidate JSON)
           │ 5. Schema Validator            │  (Zod / JSON Schema)
           │ 6. Evidence Validator          │  (Hallucination & Recall Checks)
           │ 7. Deterministic Normalizer    │  (Numeric/Whitespace Cleaning)
           └────────────────┬───────────────┘
                            │
                            ▼
                    Ollama Local API
                      (Qwen3-8B)
                            │
                            ▼
                  AUDITABLE ARTIFACTS
               ├── llm_request.json
               ├── llm_response.json
               ├── candidate_document.json
               ├── validation_report.json
               └── validated_document.json
```

## 3. Quickstart & Local Setup

### Prerequisites
- Node.js >= 20 (Node 22 recommended)
- **LM Studio** (running on `http://192.168.0.104:1234/v1` or local with model `qwen3-8b-mlx`) or **Ollama** (on `http://localhost:11434` with `qwen3:8b`)

### Step 1: Configure Environment Variables
Create or update `.env` (or copy from `.env.example`):
```env
LLM_PROVIDER=lmstudio
LM_STUDIO_BASE_URL=http://192.168.0.104:1234/v1
LM_STUDIO_MODEL=qwen3-8b-mlx
LLM_API_KEY=s

LLM_TEMPERATURE=0
LLM_TOP_P=0.8
LLM_TIMEOUT_MS=300000
LLM_MAX_RETRIES=2
LLM_THINKING=false
```

### Step 2: Install Project Dependencies
```bash
cd edmo-di-llm-backend
npm install
```

### Step 3: Run the Service
```bash
# Development mode with hot-reloading
npm run start:dev

# Production build
npm run build
npm run start:prod
```

> **Note on Resilient Startup**: The LLM engine is treated as a runtime dependency. The NestJS backend starts cleanly even if the provider is temporarily offline, reporting a `degraded` health status until the LLM server connects.

## 4. CLI Usage

The service provides the `edmo-intelligence` CLI tool:

### Extract Structured Data from Context
```bash
# Using compiled CLI
node dist/src/cli.js extract \
  --context ./examples/transcript/sophia_jones_transcript/llm_context.json \
  --output ./results/sophia_extracted

# Or using ts-node directly
npm run cli -- extract --context ./examples/transcript/boston_transcript/llm_context.json
```

### Run Evaluation Benchmarks
```bash
# Benchmark all example transcripts against Qwen3-8B
npm run benchmark

# Benchmark specific contexts
npm run cli -- benchmark \
  --contexts ./examples/transcript/sophia_jones_transcript/llm_context.json ./examples/transcript/boston_transcript/llm_context.json \
  --summary ./results/benchmark_summary.json
```

### Check LLM Health
```bash
npm run cli -- health
```

## 5. Universal REST API

### 1. Extract from Context Object
**`POST /v1/intelligence/extract`**
```json
{
  "document": {
    "id": "doc_101",
    "type": "transcript"
  },
  "context": {
    "schema_version": "llm-context-0.1",
    "document": { "type": "transcript", "page_count": 1 },
    "sections": [...],
    "tables": [...]
  },
  "options": {
    "model": "qwen3:8b",
    "prompt_version": "transcript.v1",
    "temperature": 0
  }
}
```

### 2. Extract from Context File Path
**`POST /v1/intelligence/extract-file`**
```json
{
  "context_file_path": "./results/Boston_Transcript/llm_context.json",
  "report_file_path": "./results/Boston_Transcript/llm_context_report.json"
}
```

### 3. Service & Model Health
- **`GET /health`**: Returns service and Ollama status (healthy or degraded).
- **`GET /health/llm`**: Returns detailed Ollama model info and connection status.
- **`GET /v1/models`**: Lists available models on the active LLM provider.

### 4. Interactive Swagger / OpenAPI Documentation
When the server is running, interactive Swagger UI and raw OpenAPI JSON are accessible at:
- **Swagger UI**: [http://localhost:3000/docs](http://localhost:3000/docs) (or [http://localhost:3000/api-docs](http://localhost:3000/api-docs))
- **OpenAPI JSON**: [http://localhost:3000/docs-json](http://localhost:3000/docs-json)

The Swagger interface provides:
- Live endpoint exploration and "Try it out" test execution directly in the browser.
- Complete request/response schemas with field constraints, descriptions, and examples.
- Documented error responses (`400 Bad Request`, `503 Service Unavailable`, `500 Internal Server Error`).

## 7. Artifact Structure

Each processed document writes five JSON artifacts in `results/<document-id>/intelligence/`:
1. `llm_request.json` - System prompt, user prompt, and model options sent to the LLM.
2. `llm_response.json` - Raw model output text and token metrics.
3. `candidate_document.json` - Parsed JSON directly from model interpretation.
4. `validation_report.json` - Complete schema, evidence, and hallucination audit with precision/recall metrics.
5. `validated_document.json` - Trusted, normalized EDMO JSON ready for downstream consumption.
